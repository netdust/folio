# Folio — Repository Audit & Improvement Plan

*Audited 2026-06-10 at `main` (65cb104), read-only. Six parallel audit passes (architecture, code quality, security, testing, performance, deps/devex/docs), all findings verified against source. No code was modified during the audit.*

## Executive Summary

**Overall health: B.** The code itself is unusually strong for a pre-v1 product — strict TypeScript with zero handwritten `as any`, 2,756 passing tests at better than 1:1 test-to-source file ratio, a machine-checked `ARCHITECTURE-INVARIANTS.md`, exemplary crypto/SSRF/authorization implementations, and EXPLAIN-verified index discipline. What pulls the grade down is everything *around* the code: the product cannot currently be installed by following its own documentation, the "one binary" architectural rule #1 is not actually met by the build, the Docker image is broken in three verified ways, there is zero CI, and the codebase fails its own linter with 1,732 errors because nothing ever runs it. **Top 3 risks:** (1) the delivery surface — install docs, binary, Docker — is broken end-to-end for the exact customer this product is sold to; (2) an unauthenticated magic-link endpoint silently creates new user accounts, bypassing the carefully gated `/register`; (3) two append-forever tables (`events`, agent runs) plus a per-hook SSE connection model that already caused a production "can't save" incident. **Top 3 opportunities:** a one-day CI + lint sweep that makes the existing discipline machine-enforced; cheap dedup of the ~50%-duplicated slideover family and the markdown-PATCH path; and an events-retention reaper that follows an existing in-repo pattern.

## Phase 1 — Repo Map

**Purpose.** Folio is a lightweight, self-hostable, agent-first project-management + wiki tool (markdown files with YAML frontmatter as source of truth), sold per-customer as a single binary or Docker container. Agents are first-class users via REST + MCP; AI is BYOK. Maturity: late pre-v1 (phases 0–4 of the internal roadmap shipped), single primary author working agent-assisted.

**Stack.** Bun runtime; Hono + Drizzle + SQLite backend (`apps/server`, 230 TS files); React 18 + Vite 5 + TanStack Router SPA (`apps/web`, 355 files); shared Zod schemas (`packages/shared`, pure and clean). ~120K LOC total including tests. Biome for lint/format (configured, never run). Tests: bun test (server/shared), vitest (web), Playwright (e2e, local-only).

**Architecture sketch.** `routes/` (Hono, thin-ish) → `services/` (documents, comments, agent-runs, conversations) → Drizzle/SQLite. Every write goes through `txWithEvents` and emits into a durable `events` table; two event planes consume it: a lossy in-memory `eventBus` feeding SSE (`routes/events.ts`, with seq-cursor replay), and a durable at-least-once `event-dispatcher` feeding reactors (trigger matcher). An agent runner (`lib/runner.ts`) polls for queued runs, streams from four BYOK AI providers (`lib/ai/*`), and dispatches all tool calls through one registry (`lib/agent-tools-registry.ts`) shared with the MCP endpoint. Authorization converges in `lib/access.ts` (visibility) and `executeTool` (scope ∩ caller, fail-closed).

**Key directories.**

| Path | What it is |
|---|---|
| `apps/server/src/routes/` | 20 Hono routers, one error convention (`HTTPError` → `{error:{code,message}}`) |
| `apps/server/src/services/` | Business logic for documents/comments/runs/conversations (inconsistently — see M3) |
| `apps/server/src/lib/` | The engine room: runner, tool registry, event planes, auth, crypto, access, SSRF guard |
| `apps/server/src/db/` | Drizzle schema (643 lines), 31 migrations, 20 migration tests |
| `apps/web/src/components/` | Feature-foldered UI; slideover/ contains the big duplication |
| `packages/shared/src/` | Zod schemas + pure functions only — verified no server/client leakage |
| `docs/` | 7 product docs (~3.7K lines) + 4.7MB of `docs/superpowers/` process history |
| `scripts/`, `apps/server/scripts/` | Invariant checker + hooks (good); stale `__system`-era shakeout scripts (debris) |

**Surprises.** (1) `scripts/build.ts`, documented in CLAUDE.md as the single-binary build, **does not exist**; the compiled binary serves the SPA from a cwd-relative disk path. (2) The codebase has 1,732 Biome errors despite a configured linter. (3) `SESSION_SECRET` is a required env var that is never used anywhere. (4) The repo's self-documentation of failure modes (threat-model mitigation numbers inline in code) is the best I've seen at this maturity.

## Phase 2 — Audit Report

Findings are deduplicated across the six passes and sorted by severity within dimension. *(F)* = fact, *(J)* = judgment.

### Critical

**C1. A fresh install fails at step one — onboarding is broken end-to-end.** *(F)* `routes/auth.ts:54-57` rejects the first-ever registration unless `FOLIO_ALLOW_BOOTSTRAP_REGISTRATION=true` or `FOLIO_INSTANCE_OWNER` is set — neither appears in README, `.env.example`, or INSTALL.md. Compounding: `.env.example` sets `PORT=3000` but `apps/web/vite.config.ts:5` proxies to 3001 (README contradicts itself between line 38 and its own curl examples); INSTALL.md points to a releases page that doesn't exist and names the wrong build script. A new operator following the docs hits three independent dead ends. For a product whose pitch is "installable in one command," this is the single most important finding in the audit.

### High

**H1. The "one binary" rule (architectural rule #1) is not met.** *(F)* `build:binary` compiles only the server; `app.ts:133-135` serves the SPA via `serveStatic({ root: '../web/dist' })` — a cwd-relative disk path. The 102MB `dist/folio` binary only serves a UI if launched from the right directory with `web/dist` present on disk. Nothing is embedded. CLAUDE.md's claim of `scripts/build.ts` ("React → embed → compile") references a file that doesn't exist.

**H2. The Docker story is broken in three verified ways.** *(F)* `Dockerfile:4` copies `bun.lockb*` but the repo has text-format `bun.lock` → the `|| bun install` fallback does **unpinned** installs (lockfile ignored entirely); `docker-compose.yml:13` healthchecks `/api/health` but the only endpoint is `/healthz` (`routes/health.ts:6`) → container permanently unhealthy; migrations are copied to `/app/migrations` but `auto-migrate.ts:11` resolves them relative to `import.meta.dir`, which inside a compiled binary is a `$bunfs` virtual path where the `.sql` files were never bundled *(J on the last point — image not built under read-only constraint, but the wrong healthcheck corroborates this image has never run)*. Also: image pins Bun 1.1.34 while dev runs ~1.3.x — the shipped artifact runs on a runtime nobody tests against.

**H3. No CI whatsoever.** *(F)* No `.github/`, no CI config anywhere. 2,756 tests across three suites with two different runners and a known run-from-root trap are enforced purely by local discipline. The repo's own memory records three subagent test-count misreports — exactly the failure class CI eliminates. Nothing proves the Docker build or binary compile still works.

**H4. Lint is configured but never enforced: 1,732 errors, 59 warnings.** *(F)* `bun run lint` fails today; Biome is absent from the pre-commit hooks (`scripts/hooks/install.sh` wires only migration-journal + invariants checks). A large fraction is formatter/import-organize noise — meaning the formatter is also never run. The lint signal is currently worthless.

**H5. Open self-registration via magic-link bypasses the gated `/register`.** *(F)* `POST /auth/magic-link/request` is unauthenticated with no invite check (`routes/auth.ts:144-160`), and `consume` **upserts a brand-new user** for any email (`auth.ts:177-182`). Impact bounded by default-deny grants (`lib/access.ts` — a fresh member sees nothing), but it's a real authenticated principal who can mint PATs. Attack: anyone who can reach the instance becomes a member.

**H6. No rate-limiting on login or magic-link request.** *(F)* Zero throttling middleware in the server (`routes/auth.ts:91-110`). Argon2id slows guessing but also makes each attempt a CPU-DoS lever; magic-link flooding enables email-bombing (`auth.ts:144-157`).

**H7. `events` table grows unbounded on the hottest write path.** *(F)* The only `DELETE FROM events` is the rollback scrub (`lib/events.ts:179`). Every write emits an event by architectural rule; an agent writing every 10s ≈ 3M rows/year with JSON payloads, growing the DB file, three indexes, and every backup forever. Reactor cursors + SSE replay horizons already make old rows provably dead — they're just never reaped. (A `pending_ops` reaper exists as the in-repo pattern to copy.)

**H8. Per-hook `EventSource` model collides with the browser's 6-per-origin HTTP/1.1 cap — already caused a production incident.** *(F)* `event-stream.ts:62` opens one connection per consumer; a normal project view with a slideover open mounts 5–7 (reactor-health and provider-health banners always mounted at `w.$wslug.tsx:501-502`, plus live-documents, live-document, comments, runs/activity, conversation). Overflow blocks *all* fetches to the origin — the documented "can't save / stuck on Saving…" incident. Defused behind HTTP/2 proxies, fully exposed in dev and any HTTP/1.1 deploy.

**H9. `lib/crypto.ts` and `lib/auth.ts` have zero direct tests.** *(F)* The AES-256-GCM module guarding customer AI keys has no test for tamper detection, wrong-key failure, or ciphertext format stability — a framing refactor would pass the entire suite while bricking every stored key on customer instances at next decrypt. `auth.ts`'s session-expiry branch (`auth.ts:34`) has no coverage at any layer (no wire test can hit it without clock control). The repo's own testing-workflow rule says security guards are always Tier A.

**H10. `runner.ts` is a 2,264-line dual-mode god file; `runLoop` is ~451 lines with 37 `ctx.sink` mode checks.** *(F structure, J severity)* Document runs and cockpit conversation turns share one loop discriminated by `if (ctx.sink)` at 37 sites (`runner.ts:1209-1660`); budget cap, cancel detection, confirm gate, error classification, and chain suppression live in one closure. Past calibration bugs (double-post on sink path, budget not persisting) are exactly this class. The most security-critical path in the repo is also its hardest-to-review function.

**H11. The slideover family is a maintained copy-paste fork, ~50–60% literal duplication.** *(F)* `document-slideover.tsx` (706) vs `workspace-document-slideover.tsx` (717): ~301 identical lines and an identical draft/remount/dirty-tracking lifecycle maintained twice; the fork extends to activity panels, log buttons, and ~2,000 lines of forked tests. The InlineEdit-race class of bug must be fixed in two places or diverges silently.

### Medium

**M1. Layering inversion:** `agent-tools-registry.ts:54` imports `createRunForParent`/`loadRunScopedByToken` from `routes/runs.ts:139-252` — service-grade logic living in a route file, making routes ← lib ← routes. *(F)*

**M2. Two manual-lockstep module cycles in the tool system:** import-position-dependent side-effect registration (`agent-tools.ts:518-526`) and a duplicated operator-resolution function (`agent-guards.ts:37` vs registry) that invariant 13 asks humans to "keep in lockstep" — a drift point on a security-relevant path. *(F)*

**M3. Split-brain write layering:** the markdown-PATCH branch of `routes/documents.ts:289-395` re-implements `updateDocument` inline, duplicating status validation and `agent.task.assigned` emission — ratified by the invariants doc for invariant 5 but unprotected against the two copies drifting. *(F)*

**M4. SSE invalidation storm:** any document event invalidates the whole project documents prefix (`use-live-documents.ts:33`), refetching 3–5 active list queries — each of which returns **full markdown bodies** (`services/documents.ts:381-386`) the table never renders. Together: several hundred KB of refetch per agent write, continuously. *(F breadth, J payload math)*

**M5. Pagination is server-solid, client-dead:** no web consumer reads `nextCursor` (zero grep hits); views silently truncate at 50–200 rows, and the client-side frontmatter post-filter (`documents.ts:296-310` in web) filters only the newest page — wrong result sets at thousands of docs. Project-scoped `GET /runs` has no LIMIT at all (`routes/runs.ts:280-287`) while run documents accumulate forever. *(F)*

**M6. Doc drift on agent-facing surfaces:** `docs/API.md:83-93` documents the AI-keys endpoint at a per-workspace path whose source file no longer exists (real: `/api/v1/instance/ai-keys`); API.md/INSTALL.md/CLAUDE.md all claim "libsodium" while the code uses AES-256-GCM via `@noble/ciphers`; MCP.md says 20 tools, the registry has 31; README's status line is two phases stale; PHASES.md's phase numbering now collides with the executed phase names. For an *agent-first* product, agents following API.md get 404s on the security-sensitive surface. *(F)*

**M7. Two genuinely opaque error-swallows** (out of 44 bare catches, most deliberate and documented): the crash-recovery un-wedge fallback `.catch(() => {})` at `services/conversations.ts:270-280` (the one failure mode the code calls unacceptable becomes invisible) and `eventBus.publish`'s log-free subscriber swallow (`event-bus.ts:70-75`), contrasting with the dispatcher which logs + halts + emits health edges. *(F)*

**M8. Stale `__system`-era scripts look like maintained tooling:** `shakeout-cross-ws-*.ts`, `diagnose-*.ts` (17 `__system` references) target the architecture torn down 2026-06-05; re-running them gives false signal. *(F)*

**M9. `loadConversationContext` fabricates typed `Workspace`/`Project` objects via `as unknown as` double-casts (`runner.ts:692-701`)** — empty-string IDs the type system promised were real, in the authority-adjacent runner context. Plus a repeated untyped Drizzle-row→`Document` cast cluster in `services/comments.ts`. *(F)*

**M10. No global request-body limit** (`app.ts:38-44`) — an authenticated user can POST a multi-hundred-MB document. Also Low-cluster security items: user enumeration via `/register` `EMAIL_TAKEN` + argon2 timing side-channel on login (`auth.ts:63,99-104`); documented DNS-rebinding gap in the SSRF guard (`url-allow-list.ts:6-11`); unused-but-required `SESSION_SECRET` (`env.ts:8`). *(F)*

### Low (named, not belabored)

`registerRealTools` as one 1,777-line function (merge-conflict magnet, no per-tool denial matrix — and this file already shipped a green-suite bug per project memory); `services/agent-runs.ts` bundling six subsystems incl. provider-health; `w.$wslug.tsx` firing ~40 requests on workspace mount (self-flagged O(P×T) fan-out at lines 169-189); dispatcher per-event cursor UPDATE write amplification; 7 raw `setTimeout` sleeps in web tests; 7 "TODO C11 Playwright" skip IOUs never written; root `"test": "bun test"` script inviting the documented ~650-failure cascade; drizzle-orm 0.36 (~18 months behind, matters only for the promised Postgres toggle); CLAUDE.md telling contributors to throw `HTTPException`, which has zero uses (real convention: `HTTPError` in `lib/http.ts`).

## Phase 3 — Improvement Strategy

### Theme 1: The delivery surface is the product's weakest layer — and it's the layer customers touch first.
C1, H1, H2, M6 share one root: the *inside* of the system evolved under heavy review gates while the *outside* (install docs, binary embedding, Docker, public API docs) had no gate at all — nothing fails when README lies or the Dockerfile rots. **Target state:** a stranger installs Folio from INSTALL.md alone, on both paths (binary and Docker), and CI proves both artifacts build on every push. **Principle:** the install path is a feature with acceptance criteria, not documentation.

### Theme 2: Discipline exists but is human-enforced; make the machine hold it.
H3, H4, and the stale-doc drift are one theme: this repo has more process than most funded teams, all of it running on memory and goodwill. **Target state:** CI runs the three suites + per-app typecheck + Biome + both artifact builds; Biome in pre-commit; the lint debt paid down once. **Principle:** every gate that exists only in CLAUDE.md eventually gets skipped; gates belong in machines.

### Theme 3: Two security gaps in an otherwise hardened auth surface.
H5 + H6 (plus the M10 cluster) are the only real holes in a security posture that is otherwise above grade. **Target state:** account creation requires an invite or pre-existing user; login and magic-link are throttled (SQLite-backed, honoring the no-sidecar rule). **Principle:** unauthenticated endpoints that create principals get the same scrutiny as `/register` got.

### Theme 4: Unbounded accumulation — rows, connections, refetches.
H7, H8, M4, M5 compose into the "Folio feels slow / breaks after a quarter of heavy agent use" failure: events grow forever, every tab burns the connection pool, every agent write triggers a full-body refetch storm, and views silently truncate. **Target state:** events reaper (copying the pending_ops pattern); one multiplexed EventSource per tab; targeted/debounced invalidation; list endpoints without bodies; LIMIT on project runs. **Principle:** anything an agent does every 10 seconds must have a bounded cost.

### Theme 5: Duplication where one fix must land twice.
H11, M3, M2's duplicated resolver, H10's 37-branch dual-mode loop: the recurring shape is *two copies of one behavior held in sync by vigilance*. **Target state:** one slideover lifecycle shell; one document-update path; one operator resolver; a `RunSink` interface replacing the sink branches. **Principle:** the invariants doc's own logic — converge, then cite the convergence point.

### Explicitly NOT recommending
- **Wholesale dependency upgrades** (vite 5→7, react 18→19, tailwind 3→4, zod 3→4): pre-v1, locked stack, no security forcing function found. One exception: align Docker's Bun pin with dev. Drizzle 0.36→0.44 only when the Postgres toggle work actually starts.
- **Restructuring the AI provider adapters into a base class:** the protocols genuinely differ; a shared terminal-signal contract *test suite* run against all four is the cheaper guard.
- **Structured logging / observability stack:** console-with-prefixes + in-document run error_reasons is adequate for v1 self-hosting. Revisit post-first-customer.
- **Splitting `agent-runs.ts` / `registerRealTools` aggressively:** internally clean and section-delimited; lift out provider-health and the auth helpers, leave the rest.
- **DNS-rebinding SSRF fix:** already documented as accepted; requires attacker-controlled DNS; defer.

### Definition of done (measurable)
1. CI green on every push: 3 suites + 3 typechecks + Biome + binary build + Docker build.
2. `bun run lint` exits 0; Biome in pre-commit.
3. Fresh-clone install succeeds following only INSTALL.md, both paths (verified by a person or a CI smoke job).
4. Zero unauthenticated account-creation paths; login throttled.
5. `events` row count bounded by retention config; one EventSource per tab.
6. `crypto.ts` and `auth.ts` expiry have direct Tier-A tests.
7. API.md/MCP.md spot-checks match code (the invariant-checker pattern could extend to doc citations).

### Implementation sketches — top 3

**0.1 CI pipeline.** One workflow, ~5 jobs. Key gotchas already known in-repo: server/shared tests MUST run with `working-directory` set to their package dirs (root-cwd triggers the documented ~650-failure cascade); web is `npx vitest run`, not bun test; typecheck is per-app (`bun x tsc --noEmit` × 3, no root tsconfig); the known `list-view-create.test.tsx` flake warrants one retry on the web job only. Add `bun run build:binary` and `docker build` as build-proof jobs (no smoke yet — that lands with 1.4). Start Biome as warn-only, flip to blocking after 0.4. Cache `~/.bun/install/cache` keyed on `bun.lock`.

**1.1 Magic-link gating.** Per the repo's own rules this touches an auth surface → run the threat-modeling gate on the diff first. Approach: add an `invites` check in `consume` before the upsert at `routes/auth.ts:177-182` — if no user row exists for the email AND no unexpired admin-issued invite exists, return the same generic response as success (no enumeration). Gate `request` the same way so we don't email-bomb non-users (also closes the flooding finding alongside 1.2's throttle). Keep `FOLIO_INSTANCE_OWNER` bootstrap path intact. Tests: Tier A with the full denial matrix — unknown email, expired invite, consumed invite, existing user (must still work), first-boot owner path. Gotcha: don't break the documented invite flow in `lib/email.ts:58` — that's the mechanism being promoted, not replaced.

**1.3 Single-binary embedding.** Bun's `--compile` can embed files imported with `import file from "./x" with { type: "file" }` (and `Bun.embeddedFiles` lists them). Approach: write the real `scripts/build.ts` — build web, generate a manifest module that imports every `web/dist` asset + every `db/migrations/*.sql`, then compile. At runtime: serve static from embedded files when `Bun.embeddedFiles` is non-empty, else fall back to the current disk path (dev unchanged); same dual-source pattern for `auto-migrate.ts` (read journal + sql from the manifest instead of `import.meta.dir`). Gotchas: `serveStatic` won't read embedded assets directly — you need a small handler mapping path→embedded blob with correct content-types; binary size will grow past the README's "~50MB" claim (fix the claim, not the binary); verify `_journal.json` is embedded too or boot-migration silently skips files (the documented drizzle trap). Acceptance: copy `dist/folio` to an empty temp dir, run it, register, create a document.

## Open Questions

1. **Magic-link product intent (drives 1.1):** is "anyone with a deliverable email becomes a member" ever desired (e.g., open team signup), or should account creation be invite-only? The fix shape assumes invite-only.
2. **Binary vs. folder install (drives 1.3):** is rule #1's "one binary" literal (embed everything) or is "binary + assets folder" acceptable? Embedding is ~L effort; re-scoping the rule is ~S. The sales pitch suggests literal.
3. **Events retention default (drives 1.5):** what's an acceptable retention window for the audit-trail value of `events` — 30/90/365 days? Agent-driven back-office customers may want long trails; this is a product call, not technical.
4. **Deprecation candidates:** are the `diagnose-http-chain.ts`-style scripts worth porting to the single-team model (memory cites it as the real-key proof harness), or is deletion fine?
5. **HTTP/2 assumption (affects 2.1's priority):** will every customer deployment sit behind an HTTP/2-terminating proxy (Ploi/nginx default)? If guaranteed, SSE multiplexing drops from High to Medium urgency — but dev remains exposed either way.
6. **PHASES.md's role:** is it still the canonical roadmap, or has the memory/STATE.md system superseded it? Two phase-numbering schemes currently coexist; one should win.
