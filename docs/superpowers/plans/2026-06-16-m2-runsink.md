# M2 RunSink (audit 2.6 / H10) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This is a **behavior-preserving refactor** — the acceptance bar is ZERO behavior change, proven by the existing test suite staying green UNMODIFIED.

**Goal:** Collapse the 17 executable `ctx.sink` mode-branches in `runner.ts`'s `runLoop`/terminal path into a `RunSink` polymorphism (a `DocumentRunSink` + the existing `ConversationSink`, unified behind one interface), and split the ~451-line `runLoop` per-round body into named helpers, so `runLoop` drops under ~150 lines and the inv-12 confirm-gate catch-ordering is reviewable in isolation.

**Architecture:** The 37 `ctx.sink` textual occurrences are 17 *executable* branch sites + 20 comment/JSDoc mentions. The 17 executable branches are NOT one concern — they fall into **5 behavioral buckets** (output, lifecycle/transition, cancel-detection, token-tracking, double-post-suppression). The refactor introduces a `RunSink` interface that absorbs buckets 1–4 as polymorphic methods (document impl vs conversation impl), making the `if (ctx.sink)` discriminator vanish at those sites. Bucket 5 (double-post suppression) is the subtle one: it does NOT become a method — it disappears *because* the polymorphism makes the document and conversation paths each call a SINGLE post-surface, so the "call both → double-post on sink" hazard is structurally removed. The per-round body is then sliced into named functions (`consumeStream`, `executeToolRound`, `finishTerminal`) so `runLoop` becomes an orchestrator.

**Tech Stack:** Bun, TypeScript (`strict`), Drizzle, the existing `ConversationSink` (`lib/chat-thread-sink.ts`), `executeTool` dispatcher (`lib/agent-tools.ts`), `transitionRun`/`incrementTokens` (`services/agent-runs.ts`), `createComment` (`services/comments.ts`). Tests: `bun test` from `apps/server`.

## Scope overview

This plan touches ONE file's internals (`apps/server/src/lib/runner.ts`) plus ONE new sink file, with NO change to any caller, route, schema, or wire contract. It is the back half of a refactor whose front half already shipped (M2 2.1–2.5): the `ConversationSink` *output* abstraction already exists; this plan generalizes it from "output only" to "the run's whole mode-polymorphic surface" and deletes the residual `if (ctx.sink)` checks that survived because the original sink covered output but not lifecycle/cancel/budget.

**What this is NOT:** not a feature, not a behavior change, not a fix for the known headless-MCP confirm-gate gap (inv 12 Deliberate exception — explicitly left UNTOUCHED), not a change to `executeTool`'s scope/confirm logic, not a change to any test's *assertions* (a test whose assertions must change is a behavior-change red flag — STOP and report).

**The derived `RunSink` interface** (do NOT invent beyond this — every method maps to a bucketed branch above):

```typescript
// apps/server/src/lib/run-sink.ts (NEW)
import type { RunDoneReason } from './agent-run-schema.ts';
import type { AgentRunFrontmatter } from './agent-run-schema.ts';
import type { ConversationSink } from './chat-thread-sink.ts';

/**
 * The run's mode-polymorphic surface. Absorbs the document-vs-conversation
 * `if (ctx.sink)` branches that survived M2 2.1–2.5 (the original ConversationSink
 * covered OUTPUT only; lifecycle/cancel/budget stayed as inline mode-checks).
 *
 * Two implementations:
 *   - DocumentRunSink  — agent_run document path: createComment + transitionRun +
 *     rejection-comment cancel scan + incrementTokens (persisted).
 *   - ConversationRunSink — cockpit chat path: appendMessage via the existing
 *     chat-thread-sink + in-memory token accumulator + slot-tracked liveness +
 *     no-parent (cancel = false).
 *
 * BEHAVIOR-PRESERVING: each method's two impls reproduce EXACTLY today's two
 * branches of the corresponding `if (ctx.sink)`. No new behavior.
 */
export interface RunSink {
  /** Bucket 1/4 — a turn's prose / partial output. doc → createComment(kind); conv → sink.text. */
  post(body: string, kind: 'result' | 'comment'): Promise<void>;
  /** Bucket 4 — observability tool step. doc → no-op; conv → chat-thread-sink.toolStep. */
  toolStep(step: { tool: string; summary: string; status: 'ok' | 'error' }): Promise<void>;
  /** Bucket 8 — accumulate token usage, return running totals for the budget cap. */
  trackTokens(addIn: number, addOut: number): { tokensIn: number; tokensOut: number };
  /** Bucket 5 — terminal SUCCESS. doc → transitionRun(completed, doneReason); conv → no-op (slot is liveness). */
  complete(doneReason: RunDoneReason | undefined): Promise<void>;
  /** Bucket 2/9 — terminal FAILURE, single surface. doc → (optional partial comment then) transitionRun(failed); conv → sink.text(detail). */
  fail(reason: NonNullable<AgentRunFrontmatter['error_reason']>, detail: string): Promise<void>;
  /** Bucket 6 — cancel detection. doc → post-start rejection scan; conv → false (no parent, v1 deferral). */
  wasCancelled(): Promise<boolean>;
  /** Bucket 7 — cancel handling. doc → partial comment + transitionRun(cancelled); conv → fail(cancelled). */
  cancel(): Promise<void>;
  /** True for the conversation path — gates the clean-pause turn-ends (inv 12 + ask_choice). Replaces `ctx.sink &&`. */
  readonly isConversation: boolean;
  /**
   * The UNDERLYING low-level `ConversationSink` (with `component()`/`toolStep()`),
   * threaded into `executeTool` for the `ui` tools + the inv-12 confirm gate.
   * doc impl → `undefined` (document runs pass no conversationSink today);
   * conv impl → the composed `makeConversationSink(...)` instance.
   * This is the ONE bridge between the run-loop abstraction (RunSink) and the
   * tool/confirm layer's `ConversationSink` contract — see "Wiring constraint" below.
   */
  readonly conversationSink: ConversationSink | undefined;
}
```

> **Wiring constraint (ground-truthed 2026-06-16, controller Step 2.5 — a plan-correction).** Today `ctx.sink` (typed `ConversationSink?`) does DOUBLE DUTY: it is the run-loop's mode discriminator (what `RunSink` generalizes) AND the value passed into `executeTool` at `runner.ts:1389` as `conversationSink: ctx.sink`. The tool/confirm layer depends on receiving a `ConversationSink` with `.component()`/`.toolStep()`: the inv-12 confirm gate emits its `choice_card` via `caller.conversationSink.component(...)` (`agent-tools.ts:449-463`), and `ask_choice`/`link_panel`/`folio_api` call `ctx.conversationSink.component(...)` (`agent-tools-registry.ts:2126-2187`, `folio-api-tool.ts:400-410`). `RunSink` deliberately has NO `component()` (it is a run-loop output abstraction, not a tool-layer one). Therefore `RunSink` EXPOSES its underlying `ConversationSink | undefined` via the `conversationSink` member, and the `executeTool` thread becomes `conversationSink: ctx.sink.conversationSink` (Cluster C-1). This preserves the byte-identical value reaching `executeTool` on BOTH paths (document → `undefined`, same as today's no-sink branch; conversation → the same `makeConversationSink` instance it passes today) and requires ZERO edit to `agent-tools.ts`, `agent-tools-registry.ts`, `folio-api-tool.ts`, or `confirm-gate.test.ts`.

**Deliberate non-extractions (record so reviewers don't flag them):**
- **Entry-point dispatch (312/324/438)** — `runAgent`/`runAgentResume` choosing preflight-vs-conversationPreflight and the message *source* (buildConversationMessages vs buildInitial/Resume) stays an explicit branch. These are *construction* decisions made BEFORE the sink is the right abstraction (they pick which preflight to run and which messages to build); folding them into the sink would invert the dependency (the sink would have to build messages). Kept explicit, ≤3 sites, self-documenting.
- **`executeTool` threading (1388–1389)** — passing `ctx.sink`/`ctx.conversationId` into the tool ctx is NOT a mode branch; the `ui` tools and the confirm gate need the live sink reference. Unchanged.
- **The known headless-MCP confirm-gate gap (inv 12 Deliberate exception)** — explicitly NOT closed here. Out of scope.

## Threat model

> This refactor touches the single most security-critical path in the repo: the agent/operator run loop that streams from BYOK providers, parses AI tool-call args, makes outbound requests to user-supplied provider URLs, and is the auth/confirm spine. Written 2026-06-16, BEFORE task breakdown. Because it is a *refactor*, the frame is inverted from a feature threat model: the assets are the SECURITY-RELEVANT BEHAVIORS already in place, and the attacks are ways an extraction could SILENTLY DROP one. The dominant mitigation class is therefore "a specific existing test goes RED if this breaks; if none exists, author it RED-first before the extraction." This is the `/code-review` + `/security-review` convergence target for every cluster.

### What we're defending

1. **The inv-12 confirm-gate catch-ordering** (`runner.ts:1418–1442` today) — `isAwaitingConfirmation(err)` is checked BEFORE `isFatalToolError(err)`. A needed-but-impossible confirmation throws `AwaitingConfirmationError` (a typed CLEAN-PAUSE), which must route to `postResultAndComplete` (clean turn-end), NOT to `failRun`/`isFatalToolError`. If the order inverts, a high-risk op's confirmation pause becomes a `provider_error` failure (the exact `forbidden: …requires confirmation` regression fixed 2026-06-06) — OR worse, a fatal-error path could swallow a pause.
2. **The budget/round-cap denial-of-wallet guard** (`MAX_TOOL_ROUNDS`, `fm.max_tokens` cap, `MAX_CONSECUTIVE_TOOL_ERRORS`) — the ONLY thing bounding agent spend. The token cap reads off `trackTokens`/`incrementTokens`; the round cap bounds the outer loop.
3. **The agent ∩ token ∩ caller authority clamp** — `executeTool(ctx.token, ctx.actor, …, {callerScopes, unattended, confirmerId})`. Every tool call must keep routing through `executeTool` with the SAME narrowed token + caller snapshot (invariants 2/3/15).
4. **The chain-suppression / unattended floor** — `ctx.unattended` threaded into `executeTool` so a fired (no-human) run refuses MEDIUM/HIGH config writes (invariant 7-adjacent, inv 11).
5. **The mode-isolation of output** — a conversation turn's output MUST go to its thread, a document run's to its parent's comments. The "double-post on sink path" calibration bug class is a mode-leak: conversation data reaching the document comment path, or one surface posted twice.
6. **The untrusted-data fences** — `UNTRUSTED_DATA_DIRECTIVE` on the system channel + `fenceToolResult()` on every tool result. Read-tool output (externally-authored bodies) is labelled DATA, not instructions.

### Who we're defending against

- **A prompt-injecting document/comment author** (IN scope) — content the agent reads can try to steer it; the fences + the confirm gate are the defense.
- **A model that emits a tool_call co-emitted with a refusal / off-spec done_reason** (IN scope) — the whitelist gate (`reasonAllowsToolRound`) + fail-closed terminal policy must survive extraction.
- **A leaked/over-scoped agent or MCP token** (IN scope for the clamp; the headless-confirm-gap residual is OUT of scope, inv 12 exception) — `executeTool` scope ∩ caller clamp bounds it.
- **A refactor regression** (THE primary adversary here) — an extracted method that re-derives, widens, or drops one of assets 1–6. This is what the test net defends against.
- **Insiders with the FOLIO_MASTER_KEY / direct DB access** (OUT of scope — acknowledged).

### Attacks to defend against

1. **Catch-ordering inversion on extraction (confirm-gate bypass).** Slicing the per-round try/catch into a helper reorders or drops the `isAwaitingConfirmation` BEFORE `isFatalToolError` check → a confirmation pause is mis-classified as a fatal provider error (regression) or a fatal error is mis-classified as a pause (security: a denied op could be treated as awaiting approval).
2. **Clean-pause turn-end lost (slot wedge / silent fail).** The `awaitingConfirmation`/`askedChoice` → `postResultAndComplete` clean turn-end (lines 1507, 1548) drops or its `ctx.sink` guard inverts → the turn fails instead of cleanly pausing, OR a document run wrongly runs the conversation-only clean-pause branch.
3. **Budget cap silently bypassed.** `trackTokens`/`incrementTokens` polymorphism drops the `usedIn + usedOut > fm.max_tokens` check, or the conversation in-memory accumulator resets per call instead of accumulating → denial-of-wallet.
4. **Round cap / consecutive-error cap dropped.** `MAX_TOOL_ROUNDS` outer bound or `MAX_CONSECUTIVE_TOOL_ERRORS` sub-cap lost when `runLoop` is sliced → runaway loop.
5. **`executeTool` clamp widened / bypassed.** An extracted `executeToolRound` helper re-derives the token, drops `callerScopes`/`unattended`/`confirmerId`, or calls a tool outside `executeTool` → scope escalation / unattended-floor bypass (invariants 2/3).
6. **Double-post / mode-leak on the sink path.** The `if (!ctx.sink)` partial-work suppression (line 1279) or the single-surface `failRun` discipline is lost when output goes polymorphic → a conversation turn double-posts, or document-path output reaches the conversation thread (or vice-versa).
7. **Untrusted-data fence dropped.** `fenceToolResult()` on a tool result or `UNTRUSTED_DATA_DIRECTIVE` on the system message is lost when message-building is touched → injection fence regression.
8. **done_reason whitelist weakened.** `reasonAllowsToolRound = doneReason === 'stop' || 'tool_use'` (fail-closed) or the fail-closed terminal `collectedToolCalls.length > 0` policy is laundered into "anything but max_tokens" → a refused/unknown-reason tool call executes.
9. **Cancel detection lost on the document path.** `wasCancelled()` rejection-comment scan with the INCLUSIVE `>= started_at` boundary (FIX #1) is dropped or made exclusive when moved into `DocumentRunSink` → a mid-run cancel races the start timestamp and is ignored.
10. **Slot-release / last-resort containment broken.** The `finally`-wrapped `clearConversationSlot` + `failRunLastResort` (top-level catch, never throws to the poller) is disturbed → a conversation wedges at 409 OPERATOR_BUSY, or a bad run crashes the poller.

### Mitigations required

Each maps to an attack number. The dominant mitigation is a NAMED existing test that goes RED; where the net has a gap, author the test RED-FIRST before extracting (Tier-A, per testing-workflow).

1. **Catch-ordering (attack 1).** Cluster C-3 extracts the try/catch as ONE atomic helper with the `isAwaitingConfirmation` → `isFatalToolError` → `isInvalidArgs` → recoverable order LITERALLY preserved (copy, don't rewrite). RED test: `confirm-gate.test.ts:107` (`a HIGH op … PAUSES … AwaitingConfirmationError`) + the end-to-end conversation-turn drive in `runner.test.ts` (~3096) that asserts a `completed` turn on a confirmation pause. **GAP CHECK:** confirm-gate tests hit `executeTool` directly, not through `runLoop`. Author a RED-first runner-level test that drives a conversation run whose tool throws `AwaitingConfirmationError` and asserts (a) NO `provider_error` failure, (b) the turn completes cleanly, (c) the slot releases — BEFORE the C-3 extraction. (Cluster C-3, Task C-3a.)
2. **Clean-pause turn-end (attack 2).** The `finishConfirmationPause`/`finishAskChoice` helpers keep the `sink.isConversation &&` guard + the `wasCancelled` pre-check + `postResultAndComplete(textBuf,'stop')` order. RED: the C-3a test above + the existing `ask_choice` turn-end coverage. Doc-path runs must NOT enter these branches — `DocumentRunSink.isConversation === false`. **Choice-card emission dependency (Wiring constraint):** the confirm gate's `choice_card` is emitted by the TOOL layer via `caller.conversationSink.component(...)`, fed from `executeTool`'s `conversationSink` arg — which C-1 rewires to `ctx.sink.conversationSink`. RED: `confirm-gate.test.ts` (passes `conversationSink: sink`, asserts the card) must stay green UNMODIFIED after the C-1 rewire — that is the proof the `component()` thread survived.
3. **Budget cap (attack 3).** `trackTokens` returns running totals; the `usedIn + usedOut > fm.max_tokens` check stays in `runLoop` (the cap is loop policy, the accumulation is the sink). RED: the existing budget-exceeded test in `runner.test.ts` (document path) + author a conversation-path budget test if absent (GAP CHECK in C-2). The conversation accumulator MUST be created ONCE per `runLoop` (closure), asserted by a 2-round conversation test where round-2 tokens add to round-1.
4. **Round/error caps (attack 4).** `MAX_TOOL_ROUNDS` and `MAX_CONSECUTIVE_TOOL_ERRORS` constants + their checks stay in `runLoop` (loop policy, never in a sink). RED: existing `fanout_exceeded` round-cap test + the consecutive-tool-error test in `runner.test.ts`.

RED: the delegation-fold regression tests (`runner.test.ts` asserts `ctx.token.projectIds` caller-narrowed) + a scope-denial → fatal test. The `if (!ctx.sink)` at 1279 becomes `DocumentRunSink.fail` posting its own partial-work comment; `ConversationRunSink.fail` posts once. RED: the existing "ONE sanitized error into the thread" test (`runner-error-surface.test.ts:97`) + the AF3 "successful run appends no terminal error row" test (line 148). 7. **Untrusted-data fence (attack 7).** `fenceToolResult` + `UNTRUSTED_DATA_DIRECTIVE` are NOT in scope to move (they live in message-building / result-handling, untouched by the sink extraction). 8. **done_reason whitelist (attack 8).** `reasonAllowsToolRound` + the fail-closed terminal `collectedToolCalls.length > 0` policy stay in `runLoop`/`finishTerminal` verbatim. RED: the existing dropped-tool-call / refusal / unknown-reason tests in `runner.test.ts`.

## Architecture invariants touched

Per `ARCHITECTURE-INVARIANTS.md`. Each names the convergence point the refactor must ROUTE THROUGH and must NOT re-implement inside a sink/extracted method.

- **Invariant 2 (executeTool scope double-check, `agent-tools.ts:306`).** Every tool call stays routed through `executeTool`. No sink method collapses the two.
- **Invariant 7-adjacent (chain-suppression / unattended floor).** `ctx.unattended` stays threaded into `executeTool` unchanged so the fired-run config-write floor keeps firing.
