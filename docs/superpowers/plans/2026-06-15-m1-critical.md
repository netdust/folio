## Threat model

> This threat model is for Milestone 1 (the auth-hardening + delivery + bounded-cost fixes), written 2026-06-15 at the M1 plan. It exists because 1.1 and 1.2 touch the unauthenticated principal-creation surface and 1.5 deletes durable audit-trail rows — security-rich surfaces where `/code-review` would otherwise re-discover the attack surface each round. This section is the convergence target: reviews verify against the named mitigations. It INHERITS the Phase 3 agent-runner threat model (`docs/superpowers/plans/2026-05-27-phase-3-agent-runner.md`) for the BYOK/SSRF/agent classes — this section adds only the M1-specific deltas.

### What we're defending

- **A1 — The instance principal set.** `users` rows are real authenticated principals: a user can log in, hold a session (`auth_sessions`), and mint PATs (`api_tokens`) up to their `users.role` ceiling (invariant 7). Creating an unintended `users` row creates an unintended principal. (`apps/server/src/routes/auth.ts` `magic-link/consume` upsert at lines 174–181.)
- **A2 — Login/auth CPU + the email-delivery channel.** `Bun.password.verify` (argon2id, `lib/auth.ts:18`) is deliberately slow; each `/login` and each `/magic-link/request` is an attacker-controllable lever for CPU exhaustion (login) and email-bombing a third party (magic-link `request` calls `sendMagicLink`/SMTP).
- **A3 — The user-enumeration oracle.** `/login` returns early (no `verifyPassword`) when `!user` (`auth.ts:97`), so a fast 401 vs a slow 401 leaks whether an email is registered (timing side-channel, audit M10/Low cluster).
- **A4 — The durable event audit trail + SSE replay horizon.** `events` (`schema.ts:484`) is the source of truth for the reaction plane (`reactor_cursors.last_seq`, `schema.ts:528`) AND the SSE `Last-Event-Id` replay (`routes/events.ts`, narrowed by `events_workspace_seq_idx`). Deleting an event a reactor hasn't yet consumed silently drops an agent's work; deleting below a live SSE replay horizon breaks reconnect.
- **A5 — Server availability under oversized request bodies.** No global body limit (`app.ts:38–44`) — an authenticated user (or agent token) can POST a multi-hundred-MB document, consuming memory before any handler validates it (audit M10).
- **A6 — Delivery-artifact integrity.** The binary (1.3) and Docker image (1.4) must serve the EXACT web bundle + migrations they were built with — a binary that reads a cwd-relative `web/dist` (current H1 state, `app.ts:134`) or a Docker image with an unpinned `|| bun install` fallback (current H2 state, `Dockerfile:8`) ships an artifact that diverges from what was tested.

### Who we're defending against

- **External attacker, no account (IN scope).** Can reach `/auth/*` and any unauthenticated route. Primary target of 1.1 (principal creation), 1.2 (login/magic-link flooding), A3 (enumeration).
- **Authenticated member without admin role (IN scope).** Can POST documents → target of 1.6 (oversized body) and the agent-write-volume side of 1.5.
- **A compromised/leaked agent PAT (IN scope, bounded).** Can POST oversized bodies (1.6) and drive high write volume (1.5's motivation). Bounded by scopes (invariant 2/7) for everything else.
- **A phished instance admin (OUT of scope).** If an admin is tricked into POSTing `/instance/invites` for an attacker's email, that is a social-engineering failure, not an M1 defect — the admin gate (`requireInstanceAdmin`) is the boundary and is already correct.
- **Insider with stolen `FOLIO_MASTER_KEY` / DB file (OUT of scope).** Full DB compromise is out of scope for v1 (consistent with the Phase 3 threat model).
- **DNS-rebinding / network-position attacker (OUT of scope for M1).** No M1 task makes a new outbound request to a user-supplied URL; the SSRF surface is unchanged from Phase 3 (its allow-list still applies).

### Attacks to defend against

1. **Open principal creation via magic-link consume (H5).** An external attacker POSTs `/auth/magic-link/request` with their own email (unauthenticated, no invite check, `auth.ts:141`), receives the link, GETs `/auth/magic-link/consume?token=…`, and the upsert at `auth.ts:174–181` mints a brand-new `member` `users` row. The attacker is now an authenticated principal who can mint PATs.
2. **Magic-link email-bombing a third party (H6, A2).** An attacker POSTs `/auth/magic-link/request` repeatedly with a *victim's* email; each call fires `sendMagicLink` → SMTP → an email to the victim. Unthrottled, this is an email-flood lever pointed at an arbitrary address.
3. **Login brute-force + argon2 CPU-DoS (H6, A2).** An attacker hammers `/login` with guesses; argon2id slows each guess but each attempt also burns server CPU, making the slowness itself a DoS lever. No throttle today (`auth.ts:91`).
4. **User-enumeration via login timing (A3).** `/login` skips `verifyPassword` when `!user` (`auth.ts:97`), so an unregistered email returns 401 in microseconds while a registered email returns 401 only after the argon2 verify — a measurable oracle.
5. **Audit-trail loss via over-aggressive event reaping (A4).** A retention reaper that deletes events purely by age can delete an event a reactor's cursor hasn't reached (`reactor_cursors.last_seq < deleted seq`) — silently dropping queued agent work — or below a live SSE client's `Last-Event-Id`, breaking replay on reconnect.
6. **Memory exhaustion via oversized request body (A5, M10).** A caller POSTs a multi-hundred-MB JSON/markdown body; Hono buffers it before the route's Zod validation runs, exhausting server memory (`app.ts` has no `bodyLimit`).
7. **Artifact divergence — binary serves wrong/absent UI or skips migrations (A6, H1).** `dist/folio` launched from any dir without a sibling `../web/dist` serves no UI (`app.ts:134` cwd-relative `serveStatic`), and a compiled binary's `import.meta.dir/migrations` (`auto-migrate.ts:11`) is a `$bunfs` virtual path with no `.sql` files → boot migration silently no-ops.
8. **Artifact divergence — Docker unpinned install / wrong healthcheck / stale migrations (A6, H2).** `Dockerfile:4,8` copies `bun.lockb*` (repo has text `bun.lock`) so `|| bun install` runs UNPINNED; `docker-compose.yml:14` healthchecks `/api/health` (real route is `/healthz`) so the container is permanently unhealthy; migrations copied to `/app/migrations` (`Dockerfile:27`) but the compiled binary reads `import.meta.dir/migrations` (attack 7's path).

### Mitigations required

1. **Invite-OR-existing-user gate on the consume path, provenance-marked at request.** Because there is **no `invites` table** — admin invites and self-service sign-in links BOTH insert into the SAME `magic_links` table with no provenance (see DRIFT-1 in the handoff) — the gate cannot "look up an invite." The fix adds a provenance column. **Decided approach (Option B below):** add `magic_links.kind text NOT NULL DEFAULT 'signin'` (values `'signin' | 'invite'`); `POST /instance/invites` (`instance-users.ts:258`) sets `kind: 'invite'`; `consume` (`auth.ts:174`) creates a NEW user ONLY when (a) a `users` row already exists for `link.email` (existing-user login — always allowed), OR (b) the consumed link's `kind === 'invite'`. A `kind='signin'` link for a non-existent user authenticates nothing and returns the SAME generic outcome as success (redirect to `/`) — no principal created, no enumeration. `request` (`auth.ts:141`) is additionally gated: it sends a `signin` link ONLY if a `users` row exists for the email; otherwise it returns the same `{ok:true}` 200 WITHOUT inserting a magic-link or sending mail (closes attack 2's self-service flooding of non-users). The `FOLIO_INSTANCE_OWNER` bootstrap path is untouched. **Code-checkable:** the `consume` upsert branch is guarded by `if (!user && link.kind !== 'invite') { mark used; redirect('/'); return }` BEFORE the insert; `request` is guarded by `if (!existingUser) return jsonOk(c, {ok:true})` before the insert+send.
2. **SQLite-backed per-email rate-limit on `magic-link/request`.** A new `auth_rate_limits` table (or a counters table — see Task 1.2) keyed by `(scope, key)` where `scope='magic_link'`, `key=email`; on each request, increment a windowed counter; over the threshold → `429` with the standard envelope. No sidecar (architectural rule #2). **Code-checkable:** `request` calls `checkRateLimit(db, 'magic_link', email)` before insert/send; a burst test asserts the Nth call returns 429.
3. **SQLite-backed per-IP + per-email rate-limit on `/login`.** Same `checkRateLimit` helper, `scope='login'`, keyed by BOTH client IP (from the proxy-aware header, falling back to the connection) AND email; either over-threshold → 429. **Code-checkable:** burst of bad logins from one IP → 429; test proves throttle AND window reset.
4. **Dummy argon2 verify on the unknown-user login branch.** When `!user || !user.passwordHash`, run a verify against a fixed dummy argon2id hash (computed once at module load) BEFORE returning 401, so the unknown-user path costs the same wall-clock as the wrong-password path. **Code-checkable:** the `!user` branch calls `verifyPassword(password, DUMMY_HASH)` (result discarded) before `throw UNAUTHENTICATED`; the early-return is removed.
5. **Reaper deletes only events that are BOTH older than retention AND strictly below the minimum live cursor.** Mirror `reapStalePendingOps` (`services/pending-ops.ts:197`): a single atomic chunked `DELETE FROM events WHERE created_at < cutoff AND seq < (SELECT MIN(last_seq) FROM reactor_cursors)`. The `MIN(last_seq)` floor guarantees no event a reactor still needs is deleted. When `reactor_cursors` is empty (no reactors registered yet), the floor is the current `MAX(seq)` of events drained — but the safe default is to treat an empty cursor set as "delete nothing this tick" (no reactor has committed, so nothing is provably dead). SSE replay is bounded by the SAME `last_seq` horizon (a reconnecting client cannot ask for events below what every reactor already consumed without the dispatcher having moved on). **Code-checkable:** the DELETE predicate ANDs `lt(events.createdAt, cutoff)` with `lt(events.seq, minCursor)`; a seam test proves an old event ABOVE the min cursor survives and reactors + a `Last-Event-Id` replay are unaffected.
6. **Global `hono/body-limit` middleware with env-overridable default.** Register `bodyLimit({ maxSize, onError })` app-wide in `app.ts` AFTER `logger`/`attachUser` but BEFORE the route mounts; `maxSize` from a new `FOLIO_MAX_BODY_BYTES` env (default ~5 MB); `onError` throws the existing `HTTPError` so the response is the standard `{error:{code:'PAYLOAD_TOO_LARGE',message}}` envelope at 413 (invariant 9). **Code-checkable:** `app.use('*', bodyLimit(...))` present; an oversized POST returns 413 with the standard envelope shape.
7. **Binary embeds `web/dist` + migration `.sql` + `_journal.json`; runtime serves from embedded files when present, falls back to disk in dev.** A real `scripts/build.ts` builds the web, generates a manifest module that `import`s every `web/dist` asset AND every `db/migrations/*.sql` + `meta/_journal.json` `with { type: 'file' }`, then compiles. At runtime: a small static handler maps request path → embedded blob (correct content-types) when `Bun.embeddedFiles.length > 0`, else the current `serveStatic` disk path (dev unchanged); `runMigrationsOnBoot` reads the journal + sql from the manifest when embedded, else `import.meta.dir` (dev unchanged). **Code-checkable:** `dist/folio` copied to an empty temp dir, run, serves the UI, self-migrates, and registers a user (feature-acceptance flow F3).
8. **Docker: `bun.lock` (text) with hard `--frozen-lockfile` (no fallback); `/healthz` healthcheck; Bun pin aligned to dev (1.3.x); migrations served via 1.3's embedding (no `/app/migrations` copy reliance).** **Code-checkable:** `Dockerfile` COPYs `bun.lock` (not `bun.lockb*`), `RUN bun install --frozen-lockfile` with NO `|| bun install`; `docker-compose.yml` healthcheck targets `/healthz`; `FROM oven/bun:1.3.x`; CI builds the image AND smoke-boots it to a healthy `/healthz`.

### Out of scope (explicit deferrals)

- **Per-admin invite rate-limit** — `POST /instance/invites` stays unthrottled in M1 (bounded by the admin gate; audit T5 deferral on that route stands).
- **Distributed/multi-process rate-limit** — the SQLite counters are single-process; correct for the one-binary deploy, not a multi-replica fleet (not a v1 shape).
- **Rotating `FOLIO_MASTER_KEY` without a deploy** — operational, not M1 (inherited from Phase 3 deferrals).
- **Magic-link as the ONLY signup path / disabling password register** — out of scope; `/register` keeps its existing bootstrap-gated behavior (`auth.ts:54`), this milestone only closes the *magic-link* principal-creation hole.
- **DNS-rebinding beyond the existing SSRF allow-list** — unchanged; no new outbound-URL surface in M1.
- **Streaming/chunked upload limit beyond `bodyLimit`'s buffered check** — `bodyLimit` covers the buffered-body class; true streaming uploads are not a v1 surface.
- **Reaping `conversations`/`messages`/`pending_ops` event-free tables** — out of M1 scope (1.5 is `events`-only; the `pending_ops` reaper already exists).
- **Per-email login lockout (security High-1, ACCEPTED residual)** — the per-email login rate-limit counter (CR-A1 unified its case-variants into one bucket) lets an attacker who KNOWS a victim's email lock that account out by bursting bad logins (the 429 floor is renewable each ~15-min window). Accepted for a self-hosted single-team tool: the blast radius is one known account on one instance, the lockout auto-clears, and the operator can clear the counter row directly. A CAPTCHA / progressive-backoff / per-account allow-list is not a v1 shape. Revisit if a customer runs a public-facing instance with untrusted login traffic.

## Architecture invariants touched (cite-only — `ARCHITECTURE-INVARIANTS.md` exists)

- **1.1 + 1.2 → invariants 1, 4, 17.** Inv 1 (identity is the auth-middleware primitive) — the consume path mints a session, the canonical principal-creation route; do not re-derive identity. Inv 4 + 17 (root-of-trust is session-only; principal creation is in the root-of-trust class) — `/auth/*` is correctly NOT under `wScope` (no `attachToken`), so a bearer can never reach consume; the invite-gate must preserve that. The rate-limit store is a NEW write surface but is auth-internal (no scope/role), so it rides no authorization invariant — confirm it never leaks per-email existence (mitigation M2 returns generic 200/429 identically for known/unknown).
- **1.5 → invariants 5, 8.** Inv 5 (every write goes through `txWithEvents`) — the reaper DELETEs events directly and emits NO event (a reap is hygiene, not a domain mutation; it must NOT call `emitEvent` or it would recurse the very table it prunes). This is the SAME shape as `reapStalePendingOps` (a Deliberate-exception-adjacent hygiene delete) — note it explicitly in the reaper's docstring so the invariant-auditor doesn't flag it. Inv 8 (SSE teaches WHEN to refetch; replay horizon) — the `MIN(last_seq)` floor is what keeps the SSE `Last-Event-Id` replay (`routes/events.ts`) intact.
- **1.6 → invariant 9.** The 413 MUST throw `HTTPError` → the `{error:{code,message}}` envelope, NOT a bespoke Hono `c.text('too large', 413)`. A hand-rolled error shape here is the exact bypass inv 9 names.
- **1.3 / 1.4 → no authorization invariant.** Build/delivery plumbing; touches no convergence point. (LIGHT-tier surface for review sizing.)

## Sibling-site audits (cross-cutting)

- **SA-1 (env-var convention).** Two new env vars — `FOLIO_MAX_BODY_BYTES` (1.6) and `FOLIO_EVENTS_RETENTION_MS` (1.5). BOTH must follow the established `env.ts` pattern: a `z.coerce.number().int().positive()/.min(...)` with a `.default(...)` and a comment explaining the floor — mirroring `FOLIO_PENDING_OPS_RETENTION_MS` (`env.ts:104`). Do NOT read `process.env.X` inline anywhere (the audit's I2/I3 lesson — inline reads bypass the validated singleton and NaN-silently). Audit all M1 task code for inline `process.env` reads.
- **SA-2 (the 413/429 error shape).** Both new error responses (413 body-limit, 429 rate-limit) MUST use `HTTPError(code, message, status)` from `lib/http.ts` so they emit the SAME `{error:{code,message}}` envelope the client's `formatApiError` (invariant 9) already parses. Grep the diff for any `c.json({error:...})` / `c.text(...)` / raw `new Response(...,{status:4xx})` in the M1 changes — there should be none.
- **SA-3 (the magic-link `kind` column is a new TS-union-on-a-column).** `magic_links.kind` joins the `fields.type` / `statuses.category` / `views.type` family of TS-only-or-CHECK enums (DECISIONS.md Phase 2B note). Decide once: a bare `text` column with a Zod/TS union at the boundary (no DB CHECK) is consistent with `magic_links` having no other CHECK today — prefer that for the smallest migration. If a CHECK is added, the migration must use the table-rebuild idiom (precedent: 0004/0019). Confirm the Drizzle enum and any consume-time narrowing agree.
- **SA-4 (rate-limit IP source).** The per-IP key (1.2) must read the client IP the SAME way any existing proxy-aware code does. There is NO existing IP-reading code in the server today (grep confirms), so this is a NEW convention — establish it in one helper (`clientIp(c)`), document the trusted-proxy header assumption (Ploi/nginx sets `X-Forwarded-For`), and default to the direct connection when the header is absent. Every rate-limit call site reads through that one helper.

// apps/server/src/lib/client-ip.ts
import type { Context } from 'hono';
// SA-4: single source for the client IP. Trusts X-Forwarded-For's FIRST hop
// (Ploi/nginx set it); falls back to a stable 'unknown' when absent so the limiter
// still buckets. Document the trusted-proxy assumption in INSTALL.md (1.4 doc pass).
export function clientIp(c: Context): string {
  const xff = c.req.header('x-forwarded-for');
  if (xff) return xff.split(',')[0]!.trim();
  return c.req.header('x-real-ip') ?? 'unknown';
}

```ts
// apps/server/src/lib/rate-limit.ts
import { and, eq, sql } from 'drizzle-orm';
import type { DBOrTx } from '../db/client.ts';
import { authRateLimits } from '../db/schema.ts';
import { env } from '../env.ts';

const THRESHOLDS: Record<string, number> = {
  login: env.FOLIO_RATE_LIMIT_LOGIN,
  magic_link: env.FOLIO_RATE_LIMIT_MAGIC_LINK,
};

// Returns true if the request is ALLOWED, false if it should be 429'd. Atomic
// upsert: one INSERT .. ON CONFLICT that resets the window when stale, else
// increments. Fail-OPEN on a store error (availability > hard-fail on throttle).
export async function checkRateLimit(
  db: DBOrTx, scope: string, key: string, at: number = Date.now(),
): Promise<boolean> {
  const windowMs = env.FOLIO_RATE_LIMIT_WINDOW_MS;
  const threshold = THRESHOLDS[scope] ?? 30;
  try {
    const row = await db.query.authRateLimits.findFirst({
      where: and(eq(authRateLimits.scope, scope), eq(authRateLimits.key, key)),
    });
    if (!row || at - row.windowStart >= windowMs) {
      await db.insert(authRateLimits)
        .values({ scope, key, count: 1, windowStart: at })
        .onConflictDoUpdate({
          target: [authRateLimits.scope, authRateLimits.key],
          set: { count: 1, windowStart: at },
        });
      return true;
    }
    if (row.count >= threshold) return false;
    await db.update(authRateLimits)
      .set({ count: sql`${authRateLimits.count} + 1` })
      .where(and(eq(authRateLimits.scope, scope), eq(authRateLimits.key, key)));
    return true;
  } catch (err) {
    console.error('[folio] rate-limit store error (fail-open)', err);
    return true; // F-A4 mid-flow-failure edge: allow the single request
  }
}
```
> Verify `DBOrTx` is the exported type used by `pending-ops.ts` (it imports it from `db/client.ts`). If concurrent-write atomicity needs hardening, the seam test (Step 7) is where it surfaces — bun:sqlite serializes writes, so the read-then-update is safe single-process.

```ts
// apps/server/src/services/events-reaper.ts
import { and, lt, sql } from 'drizzle-orm';
import type { DBOrTx } from '../db/client.ts';
import { events, reactorCursors } from '../db/schema.ts';
import { env } from '../env.ts';

export const EVENTS_RETENTION_MS = env.FOLIO_EVENTS_RETENTION_MS;

/**
 * Disk-hygiene reaper for `events` (audit H7). The append-only event log only
 * ever grows; every write emits a row (architectural rule). This deletes rows
 * that are BOTH older than the retention window AND strictly below the MINIMUM
 * live reactor cursor — so an event a reactor still needs is NEVER deleted, and
 * the SSE Last-Event-Id replay horizon (routes/events.ts) is preserved.
 *
 * INVARIANTS 5 + 8: this is a hygiene DELETE, NOT a domain mutation — it emits
 * NO event (calling emitEvent would recurse the very table it prunes). Same shape
 * as reapStalePendingOps. When reactor_cursors is empty no event is provably dead,
 * so the reaper is a no-op that tick. Atomic single DELETE — no SELECT-then-DELETE.
 */
export async function reapStaleEvents(db: DBOrTx, at: number = Date.now()): Promise<number> {
  const cutoff = new Date(at - EVENTS_RETENTION_MS);
  const cursors = await db.query.reactorCursors.findMany({ columns: { lastSeq: true } });
  if (cursors.length === 0) return 0; // nothing provably dead
  const minCursor = Math.min(...cursors.map((c) => c.lastSeq));
  const reaped = await db
    .delete(events)
    .where(and(lt(events.createdAt, cutoff), lt(events.seq, minCursor)))
    .returning({ id: events.id });
  return reaped.length;
}
```
> Confirm `events.createdAt` is a `timestamp_ms` column (schema.ts:496 — it is) so the `Date` comparison matches `reapStalePendingOps`'s `lt(createdAt, cutoff)` shape exactly.
