## Threat model (cluster 2.5 — operator-resolution de-cycle)

> Written 2026-06-15, BEFORE task breakdown, for the 2.5 de-cycle cluster only. The other clusters (2.1–2.4) are non-security refactors (live-update topology, cache invalidation, UI dedup, write-path unification) and do not trigger the gate — they are guarded by behavior-preservation + the existing suites, not by this section. 2.5 touches the token→agent-identity resolution path (invariant 13), an auth/identity surface, so it gets a threat model. The whole risk here is a **refactor that silently weakens an existing security guarantee** — there is no new input surface, only a code move.

### What we're defending

- The **`token.isOperator` un-forgeable marker** (`EphemeralToken`, set ONLY in `createConversationRun`; NOT a DB column, so no persisted/forged token row can carry it). It is the SOLE thing that resolves a token to the operator's code-singleton document.
- The **agent-missing guard** (`resolveAgentDocForToken` throws `agent_missing` when `token.agentId` names a non-existent/non-agent doc) — prevents a stale/deleted-agent token from silently resolving to nothing-or-wrong.
- The **role→scope ceiling** (`roleToScopes`, invariant 7) and **irreversible-op tier gate** (`effectiveRiskTier`, invariant 12) — both consume the resolved agent identity; moving the resolver must not change what they receive.

### Who we're defending against

- **External attacker / no account** — OUT of scope (no new surface; the resolver is reached only after auth).
- **Holder of a leaked/forged persisted token row** — IN scope: must NOT be able to forge `isOperator` (marker is not a column → structurally impossible; the refactor must not introduce a column or frontmatter path that reaches it).
- **A future engineer adding a new resolution site** — IN scope (the reason invariant 13 exists): after this task there must be ONE shared resolver, so a new site routes through it instead of open-coding `findFirst({id: token.agentId})`.
- **Insider with DB write** — OUT of scope (acknowledged; they can already write anything).

### Attacks to defend against

1. **Marker-check drop on move.** The de-cycle moves/merges the two resolvers into `lib/agent-identity.ts`; if the `if (token.isOperator) return getOperatorDocument()` check is reordered after the `token.agentId` lookup, an operator token (which carries `agentId: null`) would fall into the `not_agent_bound`/`agent_missing` throw and the operator breaks (the exact bug invariant 13 was named to fix).
2. **Guard divergence (the lockstep risk made permanent).** If the move leaves `agent-guards.ts`'s copy behind instead of importing the new leaf, the two drift again — a future hardening of one wouldn't reach the other.
3. **Error-shape change.** `resolveAgentDocForToken` throws MCP-shaped errors (`mcpInvalidParams`); `resolveCallingAgent` returns `undefined`. Collapsing them into one leaf must preserve BOTH call-shapes (the registry needs the throw; agent-guards needs the soft `undefined`) — a wrong unification could turn a soft "no agent" into a hard 500 or vice-versa, changing authorization behavior.
4. **New `isOperator`-reaching write path.** Introducing a column/frontmatter/serialization path that lets `isOperator` be persisted (defeating the structural guarantee).

### Mitigations required

1. **Marker-check-first, asserted by test.** The new `lib/agent-identity.ts` leaf resolves `token.isOperator` FIRST, before any `token.agentId` branch, identically to today. A Tier-A test asserts: an operator-marked token (`isOperator: true, agentId: null`) resolves to `getOperatorDocument()` and does NOT throw.
2. **Single leaf, both call-sites import it.** `agent-guards.ts` and `agent-tools-registry.ts` BOTH import the resolver from `lib/agent-identity.ts` (a leaf with no import back to either, breaking the cycle that forced the fork). The two local copies are DELETED. The invariant-13 lockstep note is removed from `ARCHITECTURE-INVARIANTS.md` in the same task.
3. **Two thin call-shapes over one core.** The leaf exports the core resolution; the throw-variant (`resolveAgentDocForToken` → MCP `agent_missing`) and the soft-variant (`resolveCallingAgent` → `undefined`) remain distinguishable. A test covers BOTH: throw-variant on missing agent throws `agent_missing`; soft-variant on missing agent returns `undefined`. (Tier A — denial paths.)
4. **No new column/frontmatter touches `isOperator`.** The task introduces NO schema change and NO write path; `isOperator` stays a non-persisted `EphemeralToken` field. Reviewer (security-sentinel, mandatory at this FULL-tier cluster) confirms.

### Out of scope (explicit deferrals)

- The **headless-MCP irreversible-op confirm-gate bypass** (invariant 12 KNOWN GAP — `effectiveRiskTier` skipped when `caller.conversationId` is absent). This task does NOT close it; it is tracked separately and unchanged by the de-cycle. Reviewers should NOT re-surface it as a new finding.
- Moving `createRunForParent`/`loadRunScopedByToken` is a **dependency-cycle break, not an authorization change** — they keep their existing scope checks (`loadRunScopedByToken` re-scopes via allowList). The move must be behavior-preserving; no new auth logic.

- `/code-review` + `/security-review` (both fire at the 2.5 cluster gate — FULL tier + a plan-time threat model exists): verify each numbered mitigation is in place; report in-place / missing / out-of-scope-per-deferrals. Do NOT free-form hunt the headless-MCP gap (deferred above).

## Task 1: SSE multiplexing — one workspace EventSource (audit 2.1)

**Files:**
- Create: `apps/web/src/lib/api/event-stream-context.tsx`
- Modify: `apps/web/src/lib/api/event-stream.ts`
- Modify: `apps/web/src/routes/w.$wslug.tsx`
- Test: `apps/web/src/lib/api/event-stream-context.test.tsx`

**Approach (read before coding):** Today each `useEventStream(wslug, filters, onEvent)` opens its own `new EventSource`. The mux inverts this: ONE `EventSource` per workspace lives in `EventStreamProvider`, opened against the UNION of all subscribers' kinds. Each `useEventStream` call becomes a subscriber registration — the hook keeps its EXACT public signature, but instead of opening a socket it (a) registers its `kinds` into the provider's union (causing the provider to reconnect with the widened `?kinds=` query when the union grows), and (b) runs each incoming frame through a client-side filter that replays the server's match logic (`project`/`parent`/`run`/`agent`/`table`/`kind`) and calls `onEvent` only on a match. This keeps all 7 consumers UNCHANGED.

**Why client-side demux is sound:** the server already names frames by kind and filters server-side per the connection's query; with the union query the provider receives a superset, and each consumer re-applies its own narrower filter. The filter predicate must mirror `routes/events.ts`: `project` → `event.projectId === filter.project`; `parent`/`run`/`agent`/`table` → match the corresponding `payload` field; `kinds` → `kinds.includes(event.kind)`.

import { describe, expect, it, vi, beforeEach } from 'vitest';
import { EventStreamProvider } from './event-stream-context.tsx';
import { useEventStream, type StreamedEvent } from './event-stream.ts';

// Capture EventSource instances opened by the provider.
class FakeES {
  static instances: FakeES[] = [];
  url: string;
  listeners = new Map<string, ((e: MessageEvent) => void)[]>();
  closed = false;
  constructor(url: string) { this.url = url; FakeES.instances.push(this); }
  addEventListener(k: string, fn: (e: MessageEvent) => void) {
    const arr = this.listeners.get(k) ?? []; arr.push(fn); this.listeners.set(k, arr);
  }
  removeEventListener(k: string, fn: (e: MessageEvent) => void) {
    this.listeners.set(k, (this.listeners.get(k) ?? []).filter((f) => f !== fn));
  }
  close() { this.closed = true; }
  emit(kind: string, data: StreamedEvent) {
    for (const fn of this.listeners.get(kind) ?? []) fn({ data: JSON.stringify(data) } as MessageEvent);
  }
}

function Consumer({ filters, onEvent }: { filters: any; onEvent: (e: StreamedEvent) => void }) {
